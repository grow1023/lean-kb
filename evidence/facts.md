## 0. 문제 제기 (슬라이드 2~4)
- [S] RAG는 질문마다 검색한 글을 프롬프트에 통째로 넣는다. 코딩 에이전트는 쓰지 않을 기억의 목차까지 요청마다 넣는다. 한 번 넣은 토큰을 모델은 대화가 이어지는 동안 요청마다 다시 읽는다
- [S] 13.8%: RAG가 넣은 4k 토큰 중 정답 근거의 비율. 범위: 발표자 지식 저장소의 개발 문항 84개
- [S] 10.3배: 4k를 한 번 넣으면 세션 안에서 드는 비용(답 호출 포함)이 답 호출 한 번 비용의 평균 몇 배인지. 범위: 한 사용자 기록을 모델 호출 없이 재생한 계산, 세션 단위 구간 7.4~12.6배
- [S] 6.9%: 기억 목차 134줄 중 한 세션에서 실제로 열린 파일의 비율(평균 9.22개). 범위: 실험 대상 PC의 대화형 메인 세션 32개. 찾아낸 것만 센 값이라 실제는 더 높을 수 있음
- [S] 기억 목차는 주당 29.9줄씩 늘었고, 이 속도면 1.57주 만에 상한 200줄에 닿는다(성장률로 계산한 값, 구간 1.1~3.6주)
- [S] 슬라이드 표기: Claude Code는 목차의 앞 200줄과 25,000자까지만 넣고 뒤쪽은 자른다
- [D] 공식 문서 표기: MEMORY.md의 앞 200줄 또는 25KB 중 먼저 닿는 쪽까지 세션 시작 때 로드한다 (code.claude.com/docs/en/memory, 2026-11-24 확인). 한글은 UTF-8에서 한 글자가 3바이트다
- [S] 규칙 줄이 목차에 있을 때 모델이 규칙 본문을 연 실행: 52회 중 16회. 규칙 줄이 목차에서 빠졌을 때: 52회 중 0회
- [S] 규칙 줄이 잘린 조건의 위반율: 53.8% (같은 과제 26개, 별도 시험)
- [S] 잘렸다는 경고는 CLI에 뜨지만, 잘린 규칙을 모델이 스스로 찾아 읽지는 않았다
- [I] 16/52 = 30.8%, 53.8% = 26개 중 14개, 23.1% = 26개 중 6개

## 1. 비용 모델과 세 가지 정책 (슬라이드 6~7)
- [S] 요청 한 번의 입력 비용 = 0.1 × 캐시에서 읽은 맥락 + 쓰기 계수 × 새로 캐시에 쓴 부분 + 캐시 밖 입력. 계수는 입력 단가 대비 비율. 쓰기 계수는 5분 캐시 1.25, 1시간 캐시 2.0. 세션 비용은 요청마다 입력과 출력 비용을 더한 합
- [S] 77.1%: 긴 대화형 세션 비용에서 캐시 읽기의 비율. 범위: 한 개발 환경의 긴 대화형 세션 20개를 모델 호출 없이 다시 계산
- [S] 0.7% → 9.4%: 4k를 한 번 넣을 때와 매 턴 넣을 때의 비용. 비용이 중간인 세션의 총비용 대비. 범위: 한 사용자 기록 재생
- [S] 줄이는 방법 셋: 덜 넣기, 같은 것을 두 번 넣지 않기, 대화를 중간에 나누기
- [S] 저장소를 통째로 캐시에 올리는 방법은 계산만 했고, 블록이 약 4.5만 토큰 이하일 때만 4k 검색보다 쌌다
- [A] 20만 토큰 블록은 질의가 아무리 많아도 검색보다 싸지지 않았다
- [S] 세 정책
  - 늘 넣기(resident): 본문을 요청마다 통째로 넣음. 비용 = 본문 크기 × 요청 수
  - 위치만(pointer): 위치를 가리키는 한 줄만 넣음. 비용 = 한 줄 × 요청 수 + 불러오기 + 손해
  - 빼 두기(page-out): 넣지 않고 필요할 때 불러옴. 비용 = 불러오기 + 손해
- [S] 가르는 기준: 필요할 때 모델이 스스로 불러올 확률
- [S] 사실 기억은 모델이 알아서 찾는다고 봄: 목차를 없애고 위치 안내와 Grep만 줬을 때 기존 전체 목차 대비 정답률 차 +0.8%p. 범위: 바꿔 쓴 질문 376문항 비공개 시험, 구간 −1.4~+2.9. 원문 질문은 채점 방식에 따라 판정이 갈렸다
- [S] 규칙은 모델이 찾지 않는다고 봄: 규칙을 늘 넣자 위반율 53.8% → 23.1% (규칙 줄이 잘린 조건, 과제 26개 별도 시험)
- [S] 규칙 블록을 넣으면 첫 요청의 토큰이 2.1배가 된다

## 2. Haema의 구조 (슬라이드 8~12)
- [S] 일곱 장치: ① 색인만 두고 불러오기 ② 질문에 맞는 예산, 같은 근거는 한 번만 ③ 문장 단위로 골라 넣기 ④ 후속 질문 풀어 쓰기 ⑤ 합치지 않고 쌓기 ⑥ 긴 대화는 중간에 나누기(세션 롤오버) ⑦ 판정을 거친 변경만 기본값으로
- [S] 층 구조(아래에서 위로)
  1. 입력: 사용자 입력, 도구 결과, 지식 저장소 문서
  2. 기억 저장(청크 색인): 지식 저장소 색인, 나눠 둔 대화 색인(선택)
  3. 불러오기(근거 고르기): 풀어 쓰기(선택), 검색, 순위 다시 매기기, 예산, 문장 고르기, 중복 제거
  4. 작업 기억(맥락 창): 늘 넣는 것(도구, 핵심 목차), 인계 메모, 불러온 근거, 대화
  5. 세션 나누기(기본 꺼짐): 세션 롤오버, 문턱, 인계 메모로 이음
  6. 기본값 바꾸기(판정으로만): 판정 게이트, 기록 재생, 처음 기준 비교, 감시
- [S] 질문 하나가 도는 순서: ① 사용자 입력이 질문이 되어 불러오기 층으로 ② 불러온 근거가 작업 기억으로 ③ 맥락이 문턱을 넘으면 다음 입력에서 세션을 나눔 ④ 작업 상태와 최근 원문을 인계 메모로 넣고 다시 시작 ⑤ 나눠 둔 대화는 기억 저장의 색인으로 ⑥ 사용자 입력마다 그 대화를 검색해 붙임. ③~⑥은 선택 설정을 켰을 때만 돈다
- [S] 질문 하나가 지나는 여섯 단계: 풀어 쓰기(후속 질문을 독립 문장으로, 선택) → 검색(BM25+bge-m3, 순위 다시 매김) → 예산 고르기(4k, 16k, 32k 중 하나) → 문장 고르기(문장 단위, 문맥 점수 순) → 중복 제거(보낸 청크는 참조 줄로) → 훅(목차 점검, 세션 롤오버, 선택)
- [S] 문장 고르기: 문장, 목록 항목, 표 한 줄, 코드 단위로 쪼개고 제목, 표 머리줄, 경로를 붙여 점수를 매김
- [S] 같은 근거는 한 번만: 앞 턴에 보낸 청크와 번호, 본문이 모두 같으면 본문 대신 참조 줄 한 줄
- [S] 한국어 개발 123문항 중 102개(83%)는 4k 예산으로 끝남
- [S] 비공개 300문항에서 상위 30개의 순위를 다시 매기자 근거 재현율 52.7% → 62.3% (4k 예산). 정답률과 기본 경로(후보 300개)는 따로 판정하지 않음
- [S] 세션 롤오버(선택 설정, 기본 꺼짐)와 기존 compact의 차이
  - 언제 줄이나: 롤오버는 문턱 뒤 첫 사용자 입력 / compact는 창이 거의 찰 때
  - 무엇을 남기나: 롤오버는 작업 상태, 최근 원문, 파일 / compact는 요약과 최근 파일
  - 지난 대화는: 롤오버는 색인해 두고 입력마다 검색 / compact는 기록 파일 위치만 안내
- [S] 긴 과제 실측(T7, T8)은 문턱 대신 "맥락이 10만 토큰 늘면 나누는" 규칙을 썼고 지난 대화 검색은 끄고 돌렸다
- [A] 도구를 부르고 결과를 받는 도중에는 나누지 않고, 캐시가 식은 순간에는 더 낮은 문턱을 쓴다
- [S] 기본값이 바뀌는 과정: 후보(설정 변경 후보를 만듦) → 고르기(개발 문항으로 하나를 고름) → 미리 고정(규칙, 데이터, 코드 해시 등록) → 레드팀(다른 모델이 허점을 찾음) → 확인 시험(비공개 문항으로 정한 대로) → 반영(반영 뒤 별도 감사)
- [S] 처음 기준 비교: 조금씩 쌓인 하락을 200회 중 200회 잡아냄. 바로 앞 단계와만 비교하면 4단계를 모두 통과한 경우가 191회. 범위: 채택마다 2%p씩 떨어지는 4단계 합성 시나리오 200회(단계마다 10,000문항). 운영에는 연결하지 않음
- [A] 단계당 700문항이면 품질이 그대로여도 43%가 실패한다
- [S] 기록된 결과를 판정 코드로 다시 판정: 세 실험(690, 700, 297문항)에서 결정이 모두 같았다(채택, 판정 불가, 검색 이득 확인)
- [S] 원칙: 만든 쪽이 스스로 채점하지 않고, 기준과 표본은 결과를 보기 전에 고정한다

## 3. 측정 결과 (슬라이드 14~17)
- [S] 문장 고르기: 넣는 토큰 34.49% 감소. 비교 대상: 기존 청크 단위 넣기. 자료: 한국어 짧은 사실 질문 399개. 정답률 92.98% → 92.23%, 미리 정한 허용 폭 안
- [S] 세션 안 중복 제거: 세션당 비용 38.7% 감소. 비교 대상: 근거를 이력에 남기는 방식(청크를 통째로 넣는 조건). 자료: LoCoMo 69세션 690턴. 정답률 81.4% → 81.7%, 허용 폭 안
- [A] 중복 제거와 문장 고르기를 함께 켠 조합의 정답률은 아직 시험하지 않았다
- [S] 통째로 넣기 대비: 같은 재현율을 내는 데 드는 토큰이 0.355배. 비교 대상: 순위를 다시 매기지 않고 통째로 넣는 방식. 자료: 영어 대화 75문항, 재현율 88.0% 기준, 점 사이를 이어 구한 값
- [S] 세션 롤오버: 입력 환산 토큰 15.1%(T7), 55.6%(T8) 감소. 비교 대상: 한 대화로 끝까지 가는 기존 방식. 자료: 긴 과제 2개 × 3회 파일럿, 검색 없이 나온 값, 기억 시험 통과
- [S] 허용 폭의 정의: 정답률 차의 한쪽 95% 하한이 −3%p보다 큰 것. 위 네 값은 자료와 비교 대상이 달라 서로 더하지 않는다
- [S] 그래프에 표기된 점(이 값만 그린다)
  - 한국어 개발 123문항: Haema 3,874토큰에 근거 재현율 99.2% / 통째로 넣기 청크 40개 16,256토큰에 95.9%
  - 영어 대화 75문항: Haema 2,994토큰 / 통째로 넣기는 같은 재현율(88.0%)에 8,437토큰(이어 구함)
- [S] 한국어 설정은 같은 개발 문항으로 골라 Haema 쪽으로 기운 값이다(슬라이드 각주)
- [A] 재현율 차이의 대부분은 순위를 다시 매긴 데서 나왔다. 순위를 다시 매긴 뒤 통째로 넣는 방식과 비교하면 Haema의 토큰은 한국어 0.921배, 영어 0.913배다. 한국어 값은 구간이 1에 걸쳐 줄었다고 단정하지 못하고, 영어 값은 이어 구한 값이라 구간이 없다
- [S] 긴 과제의 입력 환산 토큰: T7 기존 1,333,077 → Haema 1,132,181 / T8 기존 2,180,213 → Haema 968,957. 기존 방식의 최대 맥락 중앙값: T7 16.0만, T8 26.7만 토큰
- [S] 기억 의존 시험 16개: 기존 6회와 Haema 6회 모두 통과. 제약 위반: 기존은 2회에서 1개씩, Haema는 0개
- [S] 입력 환산 토큰은 캐시 읽기와 쓰기를 입력 단가로 바꿔 센 실행 평균. T7은 기존 1회가 Haema 3회보다 적어 실행 사이 변동과 구분하지 못한다
- [S] 색인만 두고 불러오기(핵심 목차만 늘 넣고 나머지는 검색): 비용 51.7% 감소(기존 전체 목차 대비, 한 개발 환경 기록 분포로 환산). 원문 질문 607문항 정답률 차 −0.2%p. 바꿔 쓴 질문은 미달(−3.2%p) 또는 판정 불가

## 4. 적용 (슬라이드 18~23)
- [S] 여덟 가지(풀어 쓴 표현)

  2. 모델이 스스로 찾는 사실은 색인과 위치 한 줄만 둔다 — 본문은 검색이나 Grep으로 불러온다
  3. 모델이 찾지 않는 규칙은 늘 넣어 둔다 — 목차 상한에 잘리지 않는 자리에 규칙 블록을 둔다
  4. 이미 보낸 근거는 다시 보내지 않는다 — 같은 청크는 본문 대신 참조 줄
  5. 청크가 아니라 문장으로 고르고, 점수에는 문맥을 붙인다 — 제목, 표 머리줄, 경로
